Part I

Session-Aware Flow

§ 01 · Session-Aware

Ingestion & enrichment

Raw events land in ClickHouse; content metadata is loaded once into an in-memory dictionary for enrichment.

1.1 · The raw event log

The Ingestor (Kafka consumer or CSV replayer) pushes events in batches into events_raw. Nothing else runs here — it's append-only.

CREATE TABLE events_raw (
  video_session_id  String,
  user_id           String,
  content_id        UInt64,
  event_type        LowCardinality(String),
  event             LowCardinality(String),
  event_ts          DateTime64(3, 'UTC'),
  platform          LowCardinality(String),
  country           LowCardinality(String),
  session_start     DateTime64(3, 'UTC'),
  ingest_ts         DateTime64(3, 'UTC') DEFAULT now64(3)
)
ENGINE = MergeTree
PARTITION BY toDate(session_start)
ORDER BY (video_session_id, event_ts);
  • ingest_ts is stamped automatically on arrival — the batch job's cursor runs on this column.
  • ORDER BY (video_session_id, event_ts) makes each session's events physically contiguous on disk.
  • PARTITION BY session_start keeps a session's entire life in one partition, even across midnight.

1.2 · Content metadata → in-RAM dictionary

The 33K content metadata rows are loaded into a ClickHouse Dictionary — an in-memory hash map that auto-refreshes every 1–5 minutes.

CREATE TABLE content_dim (
  content_id  UInt64,
  title       String,
  video_type  LowCardinality(String),
  category    LowCardinality(String),
  updated_at  DateTime DEFAULT now()
) ENGINE = ReplacingMergeTree(updated_at) ORDER BY content_id;

CREATE DICTIONARY content_dict (
  content_id  UInt64,
  video_type  String DEFAULT 'unknown',
  category    String DEFAULT 'unknown'
)
PRIMARY KEY content_id
SOURCE(CLICKHOUSE(TABLE 'content_dim'))
LAYOUT(HASHED())
LIFETIME(MIN 60 MAX 300);

Every enrichment downstream uses dictGetOrDefault(content_dict, 'video_type', content_id, 'unknown') — a RAM lookup, not a JOIN.

§ 02 · Session-Aware

Delta table generation

Two parallel paths write into cc_delta_content: an event-driven batch fold that emits +1 on activation and -1 only on VideoSessionEnd, and a time-driven staleness sweep that emits -1 after 90s of silence.

2.1 · The state that makes deltas possible

session_state holds current switches per session. Read via argMax(col, ver) GROUP BY video_session_id; written by inserting a row with a higher ver.

CREATE TABLE session_state (
  video_session_id  String,
  fg                UInt8 DEFAULT 1,     -- foreground switch
  playing           UInt8 DEFAULT 0,     -- playing switch
  ended             UInt8 DEFAULT 0,
  last_seen         DateTime64(3, 'UTC'), -- last event where counted=ON (see §2.5)
  open_run_start    Nullable(DateTime),  -- when we wrote the current +1
  content_id        UInt64,
  platform          LowCardinality(String),
  country           LowCardinality(String),
  video_type        LowCardinality(String),
  ver               UInt64               -- max event_ts (ms) so far
) ENGINE = ReplacingMergeTree(ver)
ORDER BY video_session_id
TTL toDateTime(last_seen) + INTERVAL 1 DAY;
New Semantics for last_seen

last_seen is NOT "last event we received." It's "last event received while counted=ON (playing AND fg AND not ended)." Events arriving while paused, backgrounded, or ended do NOT bump last_seen. This is what makes the 90s sweep work as the primary -1 trigger. See §2.5 for the full rule.

2.2 · The delta target

CREATE TABLE cc_delta_content (
  minute          DateTime('UTC'),
  content_id      UInt64,
  platform        LowCardinality(String),
  country         LowCardinality(String),
  video_type      LowCardinality(String),
  delta_sessions  Int64                  -- +1 or -1
) ENGINE = SummingMergeTree(delta_sessions)
PARTITION BY toDate(minute)
ORDER BY (content_id, platform, country, video_type, minute);

SummingMergeTree collapses rows sharing the ORDER BY key by adding their delta_sessions during background merges. Query safely with sum(delta_sessions) GROUP BY ....

2.3 · Two paths write into cc_delta_content

The batch scheduler runs two jobs, both every 15–30 seconds. They target the same delta table but respond to different signals.

2.4 · The narrow fan-out — cc_delta_dims

A Materialized View on cc_delta_content automatically drops content_id and copies rows to a narrower table. Fires on every INSERT into cc_delta_content.

CREATE TABLE cc_delta_dims (
  minute          DateTime('UTC'),
  platform        LowCardinality(String),
  country         LowCardinality(String),
  video_type      LowCardinality(String),
  delta_sessions  Int64
) ENGINE = SummingMergeTree(delta_sessions)
PARTITION BY toDate(minute)
ORDER BY (platform, country, video_type, minute);

CREATE MATERIALIZED VIEW cc_delta_dims_mv TO cc_delta_dims AS
SELECT minute, platform, country, video_type, delta_sessions
FROM cc_delta_content;

2.5 · The emission rules — exhaustive

Every row written to cc_delta_content comes from one of the three rules below. There are no other paths.

Rule Trigger Emission Path
+1 Event flips counted from OFF to ON
(VideoPlay or heartbeat resume while fg=ON & ended=OFF)		 Emit +1 at toStartOfMinute(event_ts). Set open_run_start. Event-driven
−1 (hard) VideoSessionEnd received while open_run_start is set Emit -1 at toStartOfMinute(event_ts). Clear open_run_start. Set ended=1. Event-driven, immediate
−1 (soft) last_seen < now() - 90s AND open_run_start IS NOT NULL AND ended=0 Emit -1 backdated to toStartOfMinute(last_seen + 90s). Clear open_run_start. Staleness sweep

The gate on last_seen

The rule that makes the staleness sweep able to close paused and backgrounded sessions is precise:

Rule for updating last_seen-- For each incoming event, in the fold:
IF (new_playing = 1 AND new_fg = 1 AND new_ended = 0) THEN
    last_seen := event_ts
ELSE
    last_seen := unchanged   -- freezes at the last "counted=ON" moment
END IF

Consequences of this rule, event by event:

Event Switch effect Updates last_seen? Why
VideoPlay, heartbeat resume playing → 1 ✓ (if fg=1) After: counted=ON
heartbeat while playing none ✓ (if fg=1) After: counted=ON
Seek, language change while playing none ✓ (if fg=1) After: counted=ON
heartbeat pause playing → 0 ✗ After: counted=OFF
AppBackgrounded fg → 0 ✗ After: counted=OFF
AppForegrounded while paused fg → 1 ✗ After: counted=OFF (playing still 0)
heartbeat while paused OR backgrounded none ✗ counted was OFF, stays OFF
VideoError, BufferStart while playing none ✓ (if fg=1) Still watching (or trying to)
VideoSessionEnd ended → 1 ✗ Emits -1 immediately via hard rule

Why this design

Short pauses (30s answering a text, then resume) generate zero delta rows — last_seen freezes during pause but is still fresh when resume arrives, so the sweep never fires. The +1 stays open uninterrupted.

Long pauses, backgrounds, wifi drops, crashes, and force-quits all funnel through the same sweep. One code path, one lifecycle.

Known Tradeoff

Peak concurrency lags by up to 90 seconds at pause / background events. If 500K sessions all pause together at the end of an ad break, the concurrency drop shows up 90s later than reality. VideoSessionEnd is exempted from this delay (immediate -1) precisely because match ends and session closes are the moments we care about most.

Sweep query — must be a seek, not a scan

The sweep runs every 15s over session_state. To keep it fast, add a skipping index on last_seen so the sweep doesn't scan every row:

Skipping index for the sweepALTER TABLE session_state
ADD INDEX idx_last_seen last_seen TYPE minmax GRANULARITY 4;

-- The sweep query then looks like:
INSERT INTO cc_delta_content
SELECT
  toStartOfMinute(s.last_seen + INTERVAL 90 SECOND) AS minute,
  s.content_id, s.platform, s.country, s.video_type,
  -1 AS delta_sessions
FROM (
  SELECT
    video_session_id,
    argMax(last_seen,      ver) AS last_seen,
    argMax(open_run_start, ver) AS open_run_start,
    argMax(ended,          ver) AS ended,
    argMax(content_id,     ver) AS content_id,
    argMax(platform,       ver) AS platform,
    argMax(country,        ver) AS country,
    argMax(video_type,     ver) AS video_type
  FROM session_state
  WHERE last_seen < now64(3) - INTERVAL 90 SECOND    -- skipping index kicks in
  GROUP BY video_session_id
) s
WHERE s.open_run_start IS NOT NULL AND s.ended = 0;
Cadence Summary

Event-driven path: every 15–30s. Writes +1 and hard -1 (only on VideoSessionEnd).
Staleness sweep: every 15s. Writes soft -1 for sessions silent > 90s.
Fan-out MV to cc_delta_dims: synchronous with each write into cc_delta_content. No lag.

§ 03 · Session-Aware

Cumulative view — computed at read time

Cumulative concurrency is never stored. It's derived from deltas by a window function every time a query asks for it.

3.1 · Why not store it?

Storing "concurrency at every minute" would require one row per (minute × platform × country × video_type × content_id) combination, forever — billions of rows, most redundant. Deltas give us one row per state change instead. A 3-hour session is 2 rows either way we look at it.

3.2 · How the cumulative is computed

ClickHouse's sum() OVER (ORDER BY minute) is a window function — a running total across sorted rows. Applied to +1/−1 deltas, it produces concurrency at every minute where a change happened.

Cumulative view — SA concurrency curveSELECT
  minute,
  sum(d) OVER (ORDER BY minute) AS concurrency
FROM (
  SELECT
    minute,
    sum(delta_sessions) AS d       -- collapse unmerged SummingMergeTree parts
  FROM cc_delta_dims
  WHERE platform = 'ANDROID_PHONE'
    AND minute >= toStartOfHour(now()) - INTERVAL 1 HOUR
  GROUP BY minute
)
ORDER BY minute;

3.3 · Why we can start from zero at the top of the hour

The batch job cuts every open run at the hour boundary — emitting both a −1 and a +1 at exactly HH:00. Net delta is zero, but every session watching at that moment is re-declared. So the running sum starting from zero at 11:00 is exact for 11:23 — no need to read anything from before 11:00, ever.

Part II

Session-Independent Flow

§ 04 · Session-Independent

Ingestion & enrichment

Same as Session-Aware — one raw log, one dictionary. Both pipelines share Stage 1.

The SI flow reads from the same events_raw table and uses the same content_dict for enrichment. There's no separate ingestion path — everything downstream branches from the same raw log.

Shared Infrastructure

Ingestion, event schema, and enrichment dictionary are identical to §01. The SA and SI pipelines diverge only after the raw log — one is triggered by the INSERT itself (SI), the other by a batch scheduler (SA).

§ 05 · Session-Independent

Sketch table generation

SI has no delta table — it stores per-minute uniq sketches. A Materialized View on events_raw fires automatically on every INSERT, no batch job needed.

5.1 · The sketch target

CREATE TABLE cc_si_minute (
  minute          DateTime('UTC'),
  content_id      UInt64,
  platform        LowCardinality(String),
  country         LowCardinality(String),
  video_type      LowCardinality(String),
  sessions_state  AggregateFunction(uniqCombined(14), String),
  users_state     AggregateFunction(uniqCombined(14), String)
) ENGINE = AggregatingMergeTree
PARTITION BY toDate(minute)
ORDER BY (platform, country, video_type, content_id, minute);

AggregateFunction(uniqCombined(14), String) stores a HyperLogLog sketch of unique session/user IDs — a fixed-size compressed representation. Sketches from different insert batches merge correctly (unlike raw counts).

5.2 · The Materialized View that fires per INSERT

CREATE MATERIALIZED VIEW cc_si_minute_mv TO cc_si_minute AS
SELECT
  toStartOfMinute(event_ts) AS minute,
  content_id,
  platform,
  country,
  dictGetOrDefault(content_dict, 'video_type', content_id, 'unknown') AS video_type,
  uniqCombinedState(14)(video_session_id) AS sessions_state,
  uniqCombinedState(14)(user_id)          AS users_state
FROM events_raw
WHERE NOT (event = 'pause'
        OR event LIKE 'download%'
        OR event_type IN ('AppBackgrounded', 'VideoSessionEnd'))
GROUP BY minute, content_id, platform, country, video_type;

The view is an INSERT trigger. When Ingestor pushes a batch of events into events_raw, ClickHouse runs this SELECT on just those new rows, enriches via dictGet (RAM lookup), filters out inactive event types, and appends sketch rows to cc_si_minute. It never re-reads history.

Known Bias

SI overcounts by ~9% at peak because it includes heartbeats fired from backgrounded apps and during pause. It's the stateless ceiling — used as a validator (SA ≤ SI) and as a fallback if the batch job stalls.

§ 06 · Session-Independent

Cumulative view — computed at read time

SI has no running sum. Each minute's concurrency is independent — no memory across minutes. Reading is a sketch merge, then a max/avg.

6.1 · Why no running sum?

SA deltas encode changes that accumulate over time — so cumulative concurrency at any minute is the running sum. SI, by contrast, encodes presence-in-that-minute directly. Every minute's sketch answers "who was here?" independently. There's no accumulation — the sketch IS the answer.

6.2 · How the cumulative is computed

uniqCombinedMerge takes multiple sketches and produces the distinct count. Applied to sketches per minute, it gives the SI concurrency curve directly.

Cumulative view — SI concurrency curve (sessions)SELECT
  minute,
  uniqCombinedMerge(sessions_state) AS si_concurrency
FROM cc_si_minute
WHERE platform = 'ANDROID_PHONE'
  AND minute >= now() - INTERVAL 1 HOUR
GROUP BY minute
ORDER BY minute;

No window function. No running sum. The GROUP BY collapses sketches from multiple insert batches (which land as separate rows in cc_si_minute until merges run) into one final count per minute.

7.2 · Peak concurrency for a window

SA · peakSELECT max(cc) AS peak
FROM (
  SELECT sum(d) OVER (ORDER BY minute) AS cc
  FROM (
    SELECT minute, sum(delta_sessions) AS d
    FROM cc_delta_dims
    WHERE video_type = 'SPORTS'
      AND minute >= toStartOfHour(toDateTime('2026-07-26 10:00:00'))
      AND minute <  toDateTime('2026-07-26 11:00:00')

7.3 · Time-weighted average

Concurrency is a step function between delta rows — hold each level for the duration until the next change.

SA · time-weighted averageWITH stepped AS (
  SELECT
    minute,
    sum(d) OVER (ORDER BY minute) AS cc,
    leadInFrame(minute, 1, toDateTime('2026-07-26 11:00:00'))
      OVER (ORDER BY minute ROWS BETWEEN CURRENT ROW AND 1 FOLLOWING) AS nxt
  FROM (
    SELECT minute, sum(delta_sessions) AS d
    FROM cc_delta_dims
    WHERE minute >= toStartOfHour(toDateTime('2026-07-26 10:00:00'))
      AND minute <  toDateTime('2026-07-26 11:00:00')
    GROUP BY minute
  )
)
SELECT
  sum(cc * dateDiff('minute', minute, nxt))
    / sum(dateDiff('minute', minute, nxt)) AS avg_time_weighted
FROM stepped
WHERE nxt > minute;

7.4 · "Right now" (zero lag)

Bypass the delta pipeline entirely — count open switches directly from session_state. Under the new last_seen semantics (only updates while counted=ON), the freshness check on last_seen alone tells us whether we've heard from a genuinely-watching session recently.

SA · live countSELECT count() AS watching_now
FROM (
  SELECT
    argMax(fg,             ver) AS fg,
    argMax(playing,        ver) AS playing,
    argMax(ended,          ver) AS ended,
    argMax(last_seen,      ver) AS last_seen,
    argMax(open_run_start, ver) AS open_run_start
  FROM session_state
  GROUP BY video_session_id
)
WHERE open_run_start IS NOT NULL          -- has an open +1 pending closure
  AND ended = 0
  AND last_seen > now64(3) - INTERVAL 90 SECOND;
-- Note: checking fg=1 AND playing=1 is redundant here — if last_seen is fresh,
-- both must be ON by the update rule in §2.5.

8.3 · Validation — SA vs SI side-by-side

Invariant: SA must never exceed SI for the same minute + filter. If it does, the state machine has a bug.

Cross-check · SA ≤ SIWITH
  sa AS (
    SELECT minute, sum(d) OVER (ORDER BY minute) AS cc
    FROM (
      SELECT minute, sum(delta_sessions) AS d
      FROM cc_delta_dims
      WHERE minute >= toStartOfHour(toDateTime('2026-07-26 10:00:00'))
        AND minute <  toDateTime('2026-07-26 11:00:00')
      GROUP BY minute
    )
  ),
  si AS (
    SELECT minute, uniqCombinedMerge(sessions_state) AS cc
    FROM cc_si_minute
    WHERE minute >= toDateTime('2026-07-26 10:00:00')
      AND minute <  toDateTime('2026-07-26 11:00:00')
    GROUP BY minute
  )
SELECT
  sa.minute,
  sa.cc AS sa_count,
  si.cc AS si_count,
  si.cc - sa.cc AS phantom_audience
FROM sa
LEFT JOIN si USING minute
WHERE sa.cc > si.cc * 1.02          -- alert threshold
ORDER BY minute;
§ 09 · Summary

Cadence at a glance

Table / View Populated by Cadence Storage
events_raw Ingestor INSERT Continuous Full log
content_dict Auto-refresh from content_dim Every 1–5 min In-RAM
session_state Batch job (write) Every 15–30s 1 row per session
cc_delta_content · +1 Event-driven fold Every 15–30s 1 row per activation
cc_delta_content · hard -1 Event-driven fold (on VideoSessionEnd) Every 15–30s, no delay 1 row per clean end
cc_delta_content · soft -1 Staleness sweep Every 15s, ~90s after silence 1 row per timed-out session
cc_delta_dims MV on cc_delta_content Synchronous with each write Narrower fan-out
cc_si_minute MV on events_raw Per INSERT (continuous) 1 sketch per minute-dim
SA cumulative Query-time window function On-demand Nothing stored
SI cumulative Query-time sketch merge On-demand Nothing stored
The Core Principle

Deltas and sketches are stored. Cumulative answers are always computed on read. This keeps writes proportional to state changes (not event volume), and query latency independent of history size — because hour-boundary cuts (SA) and per-minute independence (SI) both cap how far back any query needs to read.
