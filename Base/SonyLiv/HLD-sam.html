§ 01 · The Problem

An open session is not a watching session

A user opens SonyLIV on their phone. They watch for 5 minutes, then put the phone in their pocket. The app is still open. The session is still "alive". But are they watching? No.

The naive approach — count all open sessions — overcounts the real audience by roughly 9% at peak. Ad loads, capacity decisions, and content calls all inherit that error.

The Real Question

Count only sessions where the video is playing AND the app is in the foreground AND we heard from them in the last 90 seconds. Answer it for any filter (platform, country, content), at any minute in the past, in milliseconds.

§ 04 · Stage 0

Setup — creating the Content Dictionary

Before any data flows, we create the tables and one special object: the Content Dictionary.

What is a Content Dictionary and why do we need it?

We have two data sources:

  • events_raw — 905K playback events (what happened, when, on which session)
  • content_dim — 33K rows of content metadata (title, video_type, category per content_id)

Every event only carries a content_id number. To answer "how many people watched Sports titles?", we need to join content_id to its category. Doing that join on every query against millions of rows is expensive.

The Solution

Load content_dim into a ClickHouse Dictionary — an in-memory hash map. Looking up a content_id's category becomes a RAM lookup, not a table scan. It auto-refreshes every 1–5 minutes in the background.

§ 05 · Stage 1

On every insert — the Materialized View fires automatically

When the Ingestor pushes a batch of events into events_raw, ClickHouse automatically fires a Materialized View on that batch.

What is a Materialized View here?

It is NOT a saved query you run later. It is an insert trigger — it runs the moment rows land in events_raw, processes only those new rows, and appends results to a separate table. It never reads old data.

Which Materialized View fires here?

This is the Session-Independent (SI) view. It answers: "which sessions sent any active signal in each minute?" — with no memory of previous minutes, no state.

Why a sketch and not a plain count?

A session sends about 1.5 heartbeats per minute. If we just counted rows, one session would count as 1.5. A HyperLogLog sketch (uniqCombined) deduplicates session IDs within a minute — so one session equals one count, even across multiple insert batches.

What SI is used for

  • A fast fallback if the batch job stalls
  • An upper-bound validator: SA (true count) must always be ≤ SI (presence count)
  • The demo comparison: "here is the phantom audience we eliminated"
Known Bias

SI overcounts by ~9% because it includes heartbeats fired while the app is backgrounded (pocket heartbeats) and while paused. That is intentional — it is the stateless ceiling.

§ 06 · Stage 2

Every 15–30 seconds — the state machine (the only "brain")

SI tells us "a session sent a signal in minute M." But to know if a session was truly watching, we need to track state across minutes:

  • Was the app in the foreground?
  • Was the video playing (not paused)?
  • Did we hear from them recently (not stale)?

That requires memory across events — a state machine.

The two-switch model

We reduce all 48 event types down to two switches per session:

Why the defaults matter

  • fg = ON by default: 97% of first background events arrive after the first play event. Starting ON is correct.
  • playing = OFF by default: before VideoPlay fires, nothing is playing. Starting OFF is correct.

The delta trick — why +1 / −1 rows?

Instead of storing concurrency counts, we store the changes:

Session A starts watching at 10:02  -->  write (+1, minute=10:02)
Session A pauses at 10:17           -->  write (-1, minute=10:17)
Session B starts watching at 10:03  -->  write (+1, minute=10:03)
Session B stops at 10:12            -->  write (-1, minute=10:12)

To get concurrency at any minute: running sum of all deltas up to that minute.

minute    delta    running sum = concurrency
10:02      +1           1
10:03      +1           2
10:12      -1           1
10:17      -1           0
Why This Scales

A 3-hour session is still just 2 rows. 84% of heartbeats change no switch, so they write nothing. Database writes grow with state changes, not with event volume.

The Hour Boundary Trick

Every delta query starts at the top of the hour. Because the batch job cuts every run at hour boundaries (emitting a −1 and +1 pair), every session watching at 11:00 has a +1 row there. The running sum starting from zero at 11:00 is always correct — no need to read anything older.
